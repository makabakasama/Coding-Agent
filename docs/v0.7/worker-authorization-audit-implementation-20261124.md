# Worker 领取授权与执行审计

2026-11-24（北京时间）。本页记录第三批实现与原定验收场景。后续实测见[第三批验收](worker-authorization-audit-acceptance-20261124.md)。

## 领取与兼容

- API 和 Worker 使用同一 PostgreSQL 库、任务目录与项目登记。账号模式在数据库中按任务目录命名空间启用，普通启动可以继续处理单独的本机单用户命名空间。账号工作台应在 API 和 Worker 启动命令都传 `--auth`，尤其是 Worker 可能先启动时。已启用的命名空间即使由省略参数的 Worker 领取，也继续执行授权门禁。
- 普通任务在审批事务中绑定 `requestId`、`taskId`、`executionId` 及冻结契约。Chat 编码和返工在审批时预分配同一 `executionId`，bridge 领取核对会话权限与快照，编码任务生成后核对实际契约并把相同编号交给编码队列。普通讨论绑定提交账号与项目或会话所有者权限。
- 成员变更、放行和领取先取得同一 PostgreSQL 命名空间事务锁。领取复核同时读取并锁定申请人、放行人账号行。Worker 在同一事务内提交复核与领取，或提交未执行的终态及理由。账号模式下缺失或不匹配的授权材料会拒绝，升级前的旧记录不回填主体。普通任务副本改由领取通过后的 Worker 准备。
- 数据库故障会回滚领取事务，保留未领取记录。进程中断后的复原只接受同一执行编号的终态文件，或已经提交的 Chat bridge 调度记录。账号模式下恢复时不重新执行未完成的 bridge。领取成功之后发生撤权，可能仍有在途操作。

## 审计及结果投影

- PostgreSQL 事件按业务键追加并去重，连接申请、放行或拒绝、入队、复核、领取、结束和交付审查。事件保存编号、项目、账号或 Worker、时间、理由及审查补丁摘要。
- 队列与审计事件同事务写入。新审查结论使用 PostgreSQL 投影，与其审计事件同事务更新，保留旧的审查文件。执行材料仍按原流程落盘。Worker 重启时核对终态文件及执行编号，据此补齐已完成但尚未确认的数据库终态。证据缺失时保留中断或未知状态。
- `GET /api/projects/<projectId>/executions/<executionId>/audit` 按项目和执行编号查询，随后合并同一申请的历史事件。任务详情和普通任务、Chat 申请详情提供审计入口。

## 验收场景

| 场景 | 证据目标 |
| --- | --- |
| 普通任务放行后撤权或禁用 | 暂停领取，提交撤权后恢复。申请仍为已放行，本次执行返回明确的未启动终态，模型调用和业务文件变更均为零。 |
| Chat bridge 与编码队列之间撤权 | 分别在 bridge 领取前和编码队列领取前撤权。前者不准备副本，后者不领取编码任务，不启动编码模型。单独检查普通讨论权限。 |
| 审批人失效、范围漂移、历史无主体 | 分别禁用审批人、变更待执行范围和提交缺少证明的历史队列记录。检查理由和跨项目审计隔离。 |
| 撤权与领取竞争、故障恢复 | 控制提交顺序，确认只有一种结果生效。注入数据库投影失败与进程重启，核对编号、恢复记录和无重复启动。 |
| 正常链路与人工审查 | 用普通任务和 Chat 返工的 executionId 分别回查申请人、审批人、Worker、终态、补丁与审查人。重试放行、完成回写和同一审查决定时，业务事件保持唯一。 |
