# V0.7 后端规划：开源产品与整体功能对照

2026-11-23。目标用户是持续维护本地仓库的开发者。建议把 Coding-Agent 做成以项目和需求组织工作的编码工作台：开发者从 Chat 讨论需求，把工作交给 Agent，回来审查改动，继续提意见，之后还能查到交付和验收依据。Evaluation 继续承担固定条件下的 Agent 能力评估。

## 三种开源产品定位

| OpenCode | 开发者通过终端、桌面或 Web 与编码 Agent 工作，可选择模型提供方，配置工具、权限、项目指令和扩展。 | 作为会话工作方式的参照。看开发者能否在同一项目中自然地讨论、执行、继续追问，以及哪些项目设置能跨会话复用。[官方文档](https://opencode.ai/docs/) |
| Vibe Kanban | 个人或团队用看板安排需求，给 Agent 建立带分支和终端的工作空间，审阅差异、逐行反馈，再创建 PR 和合并。其本地服务用 Rust、Axum、Tokio 和 SQLx/SQLite。上游已公告逐步停止运营。 | 作为首要工作流参照。值得学的是需求、工作空间、审查和交付怎样连接。其工作流有文档和开源实现可查，适合做设计参照。[产品说明](https://github.com/BloopAI/vibe-kanban#overview) · [服务依赖](https://github.com/BloopAI/vibe-kanban/blob/main/crates/server/Cargo.toml) |

## 优先级与版本验收

先核对项目、需求、会话、轮次、补丁与验收材料当前怎样关联。优先补影响日常使用的两段衔接：从项目找回需求和会话，从审查反馈追到下一版交付。已有能力直接复用。第二顺位是跨任务查看工作空间和进度。团队分工、远端 PR 发布、多 Agent 调度和外部自动化留作后续产品方向，各自需要明确的用户与使用场景。

以一个仓库的两项真实需求走查上述工作流，其中一项经历两轮修改。验收时由另一位开发者从项目入口找出原需求、两轮差异、反馈对应的修改和实际检查结果，辨认另一项任务的独立进度。记录哪些步骤已经可用、哪些需要手工查目录、哪些缺少产品入口，据此确定改造清单。官方资料对照已完成，产品本机试用与本项目端到端验收待开展。

## 静态走查后的版本范围

以同仓库两项需求 A、B 为例。A 已交付第一版，用户希望针对该版反馈后继续修改；B 独立执行。下列判断来自当前产品入口和代码，尚未用真实用户任务复演。

| 用户要做的事 | 当前可见行为 | V0.7 范围建议 |
| --- | --- | --- |
| 从仓库找回 A、B | 项目历史已有普通需求列表，详情列出全部轮次并链接执行与结果。 | 保留现有需求目录。补足来源会话和当前待办，让用户能判断该继续讨论、查看执行还是审查交付。 |
| 从讨论启动 A | Chat 会把当前指令及选取的上下文交给编码任务，并保存本轮关联任务，页面已有跳到任务的入口。 | 保留讨论和授权入口，明确这次是在发起新需求还是继续已有需求；允许纯讨论会话保持独立。 |
| 对 A 第一版提出反馈，再交付第二版 | 普通需求可追加轮次，但入口只接受步数和工作空间模式，复用原需求；Chat 能表达新意见，其编码任务创建调用未传已有需求归属。 | 让用户针对选中的交付继续修改。两轮归到 A，标明第二轮基于哪一版代码、回应哪条意见。让用户可以分别查看两轮实际差异。 |
| 查看 B，稍后回来验收 A | 已有执行进度、检查和补丁。需求列表、会话、执行详情分别呈现不同信息。 | 项目层能同时辨认 B 的执行状态和 A 的审查进展。用户确认、Agent 结束和独立验收各按其实际记录展示。 |

走查入口见[项目需求与轮次页面](../../frontend/app.js)、[Chat 轮次与任务链接](../../frontend/chat.js)、[Chat 委派](../../repo_agent/backend/services/chat_execution.py)和[普通需求新轮次](../../repo_agent/backend/services/task_service.py)。上游工作流参照 [Vibe Kanban 用户指南](https://www.vibekanban.com/docs)。

**交付顺序。** 第一批打通项目需求与会话的往返，在 A、B 并存时能找回各自背景和交付。第二批支持针对已有交付返工，验收时从 A 的第一版定位意见、第二版及实际检查。第三批基于这两个流程整理项目待办与历史入口，以另一位开发者能独立接手为验收条件。跨任务进度优先复用已有查询。团队看板、第三方 Agent 接入及远端发布另行评估。

**版本取舍。** 一次重新执行可能使用重新解析的仓库版本。只有明确关联了第一版实际代码和审查意见的后续修改，才应在产品中称为针对第一版的返工。旧轮次仍按已有证据展示归属与结果。

## 首批实施记录

项目页可按项目分页读取会话，并展示需求最近一轮的调度与人工审查状态。需求详情提供原讨论、各轮结果、针对该版返工和返回上一版交付的入口。Chat 执行可明确选择新需求、继续已有需求或返工。后两种操作分别对应从本次授权的工作区起步、从选定的交付起步。

返工将反馈保存在新轮次，归入原需求。Git worktree 以原固定 commit 和核验 SHA256 的候选补丁生成独立起点，直接修改模式以原基线及执行后清单核对本轮起始文件。缺少完整材料时返回原因。人工接收或要求修改与独立实验验收分开记录。新增能力已做源码、Python 和 JavaScript 语法核对，尚未运行测试、真实模型或双需求验收场景。

### 需求从讨论到交付（2026-11-24）

项目页新增“新建需求讨论”。标题、背景和预期结果先保存为普通需求草稿，此时运行轮次为零。该需求有可重复打开的专属 Chat；讨论轮包含原始需求说明，编码权限仍需逐轮授予。专属 Chat 中发起的执行归入该需求。项目兼有普通需求和登记实验时，列表同时保留两种入口。

需求详情可返回各轮原讨论，对照父轮、返工反馈和检查，并打开最近已由用户接收的版本。新一轮尚在执行时，旧的已接收版本仍可单独查阅。单项目双需求、其中一项返工的真实验收仍待开展。

## 定向验收完成后的收尾计划（2026-11-25）

账号与会话、项目成员与审批、Worker 领取复核与审计、双需求交接四组定向验收已完成。双需求场景使用真实 PostgreSQL、Redis、HTTP API、独立 Worker 和 Edge，模型由脚本夹具提供。另一位开发者从项目首页查到了 A 的两版交付及接收记录，也确认 B 等待实例管理员放行。见[双需求交接验收](double-requirement-handoff-acceptance-20261124.md)。

1. 先明确候选版本的文件范围和源码基线。当前工作区混有 v0.6 历史资料及其他本地改动，按文件核对 v0.7 所需源码、现有测试和说明，保持工作区原有改动。
2. 在同一候选基线上做一次合并回归。沿用现有定向用例，优先覆盖本地单用户与账号模式、API 和 Worker 联动、CLI 和 SSE、两轮返工及审批审计。使用隔离数据与脚本模型，记录实际通过、失败和跳过项。运行范围由当次授权确定。
3. 回归通过后，汇总源码范围、复跑方式、证据入口和部署边界，供后续冻结决策使用。缓存收益需要另行测量，真实模型求解继续按 Evaluation 口径验收。

## 本机冻结准备（2026-11-25）

合并集成复验已通过。当前工作区逐文件核对了复验清单中的 175 项，SHA256 全部一致。清单标识了通过复验的内容，实际复跑还依赖指定的 PostgreSQL、Redis、Edge 和脚本模型夹具。见[合并集成记录](integration-acceptance-20261125.md)。

1. 从通过复验的内容取出源码、依赖、测试和复跑夹具，加入启动说明及 V0.7 验收索引。复验清单包含本机夹具，冻结时一并保留可复跑副本。V0.6 历史资料、无关改动、密钥和个人配置留在原位置。

部署范围为本机可信协作。性能、向不可信用户开放执行、发布到远端另行评估。
