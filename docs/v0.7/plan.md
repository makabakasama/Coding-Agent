# v0.7 后端路线

2026-11-23，进入规划阶段。目标是让用户通过后端提交一个仓库任务，在 Worker 独立运行 Agent 期间查询进度，结束后从同一任务取回补丁、测试记录和终止原因。v0.6 的模型求解成绩作为 Agent 能力基线。

## 已有基础

API 与独立 Worker 已经使用 PostgreSQL 持久化队列。普通任务和 Chat 分别有领取逻辑，Worker 有心跳、执行槽位和结束处理。先从普通编码任务入手，核对共享 Worker 的行为及已有验收材料，再决定需要修改什么。[Worker 说明](../worker-pool.md) · [数据库任务说明](../database-tasks.md)

## 推进顺序与交付

| 批次 | 工作 | 验收证据 |
| --- | --- | --- |
| 1. 正常交付 | 沿现有 API、任务队列、Worker、Agent 执行和结果读取入口，梳理任务 ID、执行 ID、状态及落盘责任；标明数据库事务与文件写入的边界。 | 一张以真实入口为依据的时序图，一张状态转换表，一份可重复使用的正常任务样例。每个结论附源码或运行证据；先区分已有能力和待验证行为。 |
| 2. 并发与恢复 | 按首批发现选一个影响交付的场景，优先核对并发领取、Worker 中断或结果归档后状态回写中断。明确哪些状态允许重试，哪些需要人工确认。 | 用任务与执行 ID 对齐 API、数据库和产物；说明另一 Worker 能否重复领取、异常后用户能看到什么、已有补丁能否取回，以及恢复是否触发新的模型调用。 |
| 3. 服务测量 | 在固定负载下分别测量提交延迟、排队时长、执行时长和状态查询延迟。将模型等待与服务开销分开。 | 记录环境、样本数、并发度及失败数；对可复现瓶颈给出前后数据。面试演示从提交一个任务一直到取回结果。 |

首批先交付只读契约梳理，优先检查 `repo_agent/backend/routers/task_http.py`、`repositories/task_queue.py`、`services/worker_pool.py`、`services/task_execution.py`（后三项均相对于 `repo_agent/backend/`）。以实际调用关系为准。后续实施和测试按用户授权推进。
