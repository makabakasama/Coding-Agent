# V0.5 真实模型跨文件演示方案

日期为 2026-11-10。当前为实施前方案核对，真实 Provider 调用和新测试尚未启动。

## 本轮要回答的问题

使用现有执行机制，让真实模型自主定位、创建 parsing.py、修改 caller.py、运行固定检查、更新带证据的计划并交付。在独立副本核验保存的补丁，分别记录代码效果、执行机制利用及证据完整性。

演示目标采用合成项目，模型采用真实 Provider。已有脚本模型的 7 项验收和协议/前端检查保留原结论。本轮结果只描述该模型在这一需求和预算下的一次实际表现。

## 先冻结验收条件

1. 复用离线案例的初始 caller.py 和 tests/test_delivery.py，逐字节保存、计算 SHA256；原三项行为检查原文保留。
2. 现有三项只验证 caller.parse 的正常、空和非法输入行为，尚不足以自动证明模块委托关系。因此另行冻结独立审查标准 C，确认 parsing.py 有实际解析职责、caller.parse 实际复用该模块、两个业务文件按需求交付。C 在模型运行前确定，独立于原测试 R，不能在看过模型答案后临时调整。
3. 模型可自由选择合理函数名和实现方式。任务说明只提供目标、现有入口、允许路径、固定检查及步骤/证据要求，具体工具顺序与补丁由模型决定。
4. 验收分别给出代码检查、跨文件结构审查、机制利用和独立副本复验结论。模型 finish 与步骤全勾选作为声明记录。

## 固定基线与新副本

将合成初始项目固定为准确 Git commit G，记录生成来源及本轮唯一北京时间标识。若 R 已纳入 G，记录其路径、版本和哈希。C 单独保存为运行前的审查清单。

每轮建立新的 Agent 副本和 verify-01 副本，均来自同一 G+R。Agent 运行前核对解释器、实际导入路径、依赖与检查配置，保存原三项检查的目标失败结果。独立副本验收时也先确认相同初始失败。

材料建议沿用 experiments/v05-cross-file-demo/inputs/、workspaces/，以及 runs/v05-cross-file-demo/run_<ID>/ 的 experiment.json、summary.md、repair/、verify-01/。该目录分类沿用项目约定，报告将本轮明确标为合成项目的新功能演示。

## 真实执行入口

推荐采用现有工作台 API → PostgreSQL 队列 → 独立 Worker → TaskExecution → OpenAICompatibleProvider → 工具 → 交付结果的路径，运行前只读核对当前服务配置及可隔离的实验队列。

使用专用实验任务存储、项目配置和运行/副本目录，确认实验 Worker 可领取的队列只包含本轮任务。具体数据库隔离方式在准备阶段确认，避免启动 Worker 触发其他已排队任务。使用现有的准备、入队、事件和结果接口，保留请求/响应及状态记录。

若环境仅支持同步 TaskExecution.run_claimed，可单独验证核心执行链，报告据实际入口命名；工作台 API/队列/独立 Worker 的联调结论需对应其实际运行。

TaskService 的 model_factory 在当前代码中会把 source 标成 injected_test_model。因此真实演示走默认 Provider 路径，保持 source=configured_provider；准备时核对实际生效的 profile、配置模型名及非敏感运行参数。

## 一次运行的建议预算

- 首次正式运行建议最多 20 次模型决策，包含计划更新、非法调用反馈和 finish。该值为方案建议，实施前确认。
- 正式真实模型运行一次。传输重试沿用实际 Provider 配置并单独计数，保留每次请求事件；协议错误和工具失败按现有预算反馈。
- 依赖与解释器在准备阶段固定，模型开始后沿用既有工具和授权范围。
- 保留耗尽预算、模型报错和不完整交付。之后如需重复模型运行，新建轮次和副本，独立保存结果。
- 记录实际返回的 token/缓存用量。缺失字段标为未知，失败请求的用量可能无法取得；费用需有实际计费依据才记录金额。

## 观察与记录

演示驱动记录实际出站 messages/tools、可取得的真实响应、原始工具观察、状态尾、决策/传输次数及用量；鉴权头、密钥和完整环境变量排除在记录之外。观察器透传真实请求与响应，其自身代码及配置一并留档。

核对固定规则/任务/工具的指纹、每轮最新计划及剩余预算，尤其检查工具失败或检查结果如何影响下一轮实际请求。汇总计划修订、观察引用、创建/修改/检查动作和模型终止原因。

同时保存 Agent 自身源码与未提交改动、运行配置、解释器/依赖、输入清单、基线输出、每次工具结果、实际 Diff 和最终候选文件。导出的 P 单独保存并计算 SHA256，审查其路径、测试和配置完整性。

## 独立副本验证

verify-01 恢复相同 G+R，核对源码导入位置及环境，并记录初始检查失败。随后只应用保存的 P，核对最终业务文件与原候选的哈希、保护文件和固定测试哈希，再运行原三项检查并按 C 审查真实调用关系。

验收流程使用固定命令和独立进程；模型声明保留在单独字段。对原 Agent 副本的原地复测另行标记。重复验收追加 verify-02 等记录。
