## 问题与目标

第一批补齐新建文件，第二批补齐分页和范围搜索。实施前 Agent.run 仅有工具历史、步数、编辑次数和最后检查状态。本轮已接入结构化步骤、最新状态和剩余项，目标是让跨文件任务从拆解到交付可追踪；运行效果待用户安排验证。计划状态由模型报告，实际检查和独立验收另行给出。

## 最小范围

1. 复杂任务可建立和更新小型步骤列表，包含稳定 ID、目标、状态、证据引用或阻塞原因；简单读取和单点修改可以不建计划。限制条目数量和文本长度，避免计划消耗过多预算。不新建独立规划 Agent。
2. 程序校验步骤状态与引用合法性，保留修订记录。工具调用和对应结果继续正确加入 messages；下一轮同时可见最新剩余项与剩余决策预算。更新计划本身计入现有决策预算，不增加自动重试或额外循环。
3. 使用现有 trace、任务事件和交付结果保存进度；前端只加当前步骤、剩余项和最终结果的简洁展示。重开页面可查看保存记录，不等于 Worker 中断后能续跑模型。
4. finish 对已有计划做一致性检查：存在未完成项时不能声明全部 completed，可以 blocked/incomplete 结束并保留剩余项。未建计划的旧调用保持兼容；全部勾选也不能自动标为测试通过。模型自报证据与实际工具/检查记录分开。

本轮 decisions._validate 已扩展到步骤数组和对象的严格校验，计划由 Agent 管理，文件工具继续承担路径权限职责。RecordedAgent 已贯通新进度字段和结构化脱敏，协议及运行验证后续由用户安排。

### 上下文分层与执行组织

2026-11-10 实施前核对与本轮目标如下。表中下一步契约现已接入代码，运行结果待验证。

| 部分 | 当前实现 | 下一步契约 |
| --- | --- | --- |
| 系统规则 | Agent.run 首次放入 SYSTEM_PROMPT，运行中沿用 | 每轮使用同一份运行内固定规则 |
| 工具定义 | Provider.decide 通过与 messages 并列的 tools 字段发送 TOOL_DEFINITIONS | 冻结本轮定义及顺序，记录版本/指纹 |
| 任务描述 | 后端将任务类型说明、Frozen task contract、路径与检查约束交给 Agent，作为首条 user 任务消息 | 作为本轮固定任务输入，保留需求与验收条件 |
| 执行历史 | 持续追加 assistant 工具调用、tool 结果及非法协议/finish 反馈，保留完整运行内对话 | 按发生顺序保留合法消息配对与 Provider 所需元数据 |
| 当前执行状态 | 仅有 Python 中的步数、编辑计数和最后测试状态；结构化状态尾仍待实现 | 每次调用前生成一份最新 runtime_state，作为消息尾部的独立上下文 |

目标请求结构为固定 tools 配置，以及 messages 中的“固定 system + 固定任务描述 + 累积历史 + 本轮状态尾”。工具定义在 API 请求中保持独立字段。该组织提供可校验的稳定输入，服务端内部拼接和缓存效果仍以实际 Provider 证据为依据。

建议在 Agent 中建立一个清晰的模型输入组装入口。底层维护固定任务输入和仅追加的历史，model.decide 接收本次生成的消息列表。状态尾只存在于本次请求副本，下一轮由最新状态替换，避免将旧状态副本不断追加到永久历史。状态尾使用普通上下文消息，模型计划和仓库内容继续按声明/数据处理，系统规则与冻结需求保持原有约束。

状态尾只放已用/剩余决策数、计划修订号、当前/剩余/阻塞项、当前编辑修订号、最新检查状态及必要的证据 ID。源码、完整测试输出和完整观察正文通过已有工具历史与日志保存；状态栏通过引用定位这些材料。

本轮实施顺序如下。

1. 先完成上下文组装与预算状态尾，确保无计划任务也能看见剩余决策数。
2. 再接 update_plan、观察 ID 和编辑/检查修订状态，让状态尾显示实际进展。
3. 接 finish 一致性与所有退出路径，然后贯通已有事件、结果和工作台。
4. 记录固定部分指纹、历史消息数、状态尾长度及总输入字符量。Provider 若返回实际 token/缓存用量，可按可用字段保存；缺少这些字段时明确为未知。后续依据实际增长记录评估历史摘要或压缩需求。

新增验收重点包括固定部分跨轮不变、状态尾始终最新且仅一份、历史 assistant/tool 配对完整、错误反馈仍进入下一轮，以及同一决策的传输重试复用同一请求。trace 保存分层指纹和实际状态快照，Provider 测试捕获真正发出的 payload 核对顺序及内容。

现有部分离线模型用 messages[-1] 直接读取最后工具结果；独立状态尾会改变末条消息的位置假设。实施时应核对这些调用方，改为按消息角色/工具调用 ID 取对应结果，并验证旧任务的完成、检查及文件行为兼容。

### 步骤工具和修订

已新增 update_plan(steps, reason)，由 Agent 处理，首次和修订均提交完整列表。steps 为 1–8 项，每项含 id、goal、status、evidence_refs、blocked_reason。goal 最多 300 字符，reason 和 blocked_reason 最多 1000 字符，每项最多 8 个引用。协议及语义路径校验额外字段、重复 ID、类型和文本上限。

| 状态 | 条件 |
| --- | --- |
| pending | 保留为尚未完成的工作 |
| in_progress | 全部步骤最多一项处于此状态 |
| completed | 至少引用一条已存在的实际工具观察，记录其事实与检查状态 |
| blocked | 附具体阻塞原因，可引用失败观察 |

首版建议保留已有 ID 和目标，只允许追加、重排及状态更新，包括重新打开 completed 项。未完成项不能从列表中直接消失。每次修订保留 revision、reason 和原列表，避免模型通过删除目标绕过 finish 检查。目标合并和取消协议留待实际需要时扩展。

### 程序证据与预算反馈

- 实际文件工具执行后，由程序分配本轮唯一的 observation_id，与结果一起反馈模型并写入 trace；已有 tool_call_id 继续负责协议配对。
- evidence_refs 只能引用本轮已经发生的工具观察，拒绝未知、未来和其他运行的 ID。update_plan 和 finish 自身的声明不能充当代码交付证据。
- 观察表保留动作、路径、applied、可用文件哈希、测试结果及日志标识，区分编辑、读取、失败检查和通过检查。引用存在不能自动证明任意自然语言目标得到满足，最终仍需实际修改、固定检查和范围审查。
- 建议用编辑修订号关联测试观察，后续编辑使旧检查证据标为过期；完成步骤引用旧检查时反馈待核实状态。
- 每次 model.decide 前，程序附最新 runtime_state，包含计划修订号、当前步骤、剩余/阻塞项、最后检查状态、已用及剩余决策数。建议 remaining_decisions = max_steps - current_step + 1，包含即将进行的本次决策，finish 也需一次决策。
- update_plan、非法协议反馈和被拒绝的 finish 均消耗现有决策预算。Provider 传输重试另行记录。最新状态作为本次输入的独立上下文附加，避免重复计划不断累积进永久对话；trace 记录实际发送的状态，区分模型声明与程序事实。

### finish、退出和工作台

未建计划的旧任务沿用原规则。已建计划且存在 pending、in_progress、blocked 或已知过期检查证据时，completed 请求获得明确反馈，允许继续执行或以 incomplete/blocked 结束。全部 completed 只通过计划一致性校验，检查通过状态继续根据实际结果判定；更新步骤不能抹掉已发生的检查失败。

正常 finish、预算耗尽和模型异常均保留当前计划、修订号和剩余项。Worker 中断时展示最后保存进度及待核实状态，不能把旧 in_progress 当成实时执行。

已在事件流接入 progress_updated 摘要和最终结果的可选 progress 对象。运行页面展示最后保存步骤与预算，结果页对照步骤声明和工具事实；刷新沿用既有入口，文本脱敏/转义和旧记录缺字段路径已适配。界面运行效果待验证。

## 范围外与求职价值

本批不含多 Agent、RAG、长期记忆、沙箱、模型断点续跑或自动反复执行。求职交付应展示：一个任务如何拆解、工具失败怎样反馈、预算结束如何保留未完成工作、最终证据如何对应需求；配一个可重放的离线案例和另行授权的真实演示。不能把进度列表本身包装成能力提升的实验证据。
