## 首批选择依据

规划时核对的基线中，core/decisions.py 的原生工具只有 list_files、search_code、read_file、replace_lines、run_tests、finish。apply_patch/replace_text 属于兼容旧调用，不对真实模型公开。当前工作区草稿已增加 create_file，但该草稿仍待评审。

该基线中，core/tools.py 的 replace_lines 必须持有已读取文件的快照；read_file 仅在存在可显示行时保存 snapshot_id。因此基线原生工具存在新建文件和空文件编辑缺口。底层存在创建文件的补丁能力，不等于模型已具备该能力。草稿已尝试补齐两项能力，完成情况须按下述验收核对。

这是可从代码确认的能力缺口，不需要先让其他项目产生一个需求才能处理。先补这个缺口，比增加一个计划面板更直接支持新增模块与多文件功能交付。

历史记录显示过步数耗尽、前端文件不可见、无修改就结束等情况，但部分轮次运行旧源码。没有将这些失败全部归因为当前的新建文件缺口。V0.4 已增加空完成反馈，不重复实现这条规则，也不把旧失败当成当前版本仍有相同问题的证明。

## V0.5 第一批：原生新建文件与空文件编辑

### 用户可见成果

收到新增模块类任务后，Agent 可以在授权范围新建源码文件，修改现有调用方，运行固定检查，并在结果页展示所有实际变化。直接模式撤回能够删除本轮新增文件；普通目录不需要人为创建 .git。

### 建议实现

1. 原生 create_file(path, content)：只创建不存在的受支持文本文件。复用已有路径、范围、保护目录和只读限制；目标已存在时拒绝，绝不退化成覆盖。
2. 允许创建授权范围内缺失的普通父目录；拒绝路径逃逸、符号链接/重解析点以及敏感或受保护路径。写入时再次检查路径，文件使用排他创建处理同名竞争；失败不报告已完成。
3. 内容采用明确的 UTF-8 规则，初始上限建议 60000 字符，空内容合法。返回实际路径、SHA256、写入结果和 applied；记录完整工具观察。
4. 空文件读取返回有效版本快照；增加仅用于空文件的快照写入方式（具体参数与现有 replace_lines 的兼容性在实施时确定），变更前核对原字节，文件被外部修改后拒绝旧快照写入。
5. 接通 Agent 成功编辑计数与 last_test_passed 失效、TaskRepoTools 权限检查、运行 Diff、修改范围审查和直接模式撤回。不能只把函数放进工具列表而遗漏收尾和验收。
6. 更新工具提示与文档；保持旧工具消息、历史结果和既有编辑行为兼容。

现有测试和验收配置仍受保护，新建工具不能用来写入或绕过这些路径。不增加任意 shell 工具、不同时重写调度或引入多 Agent。

## 第一批实施前评审与执行顺序

以下为推荐方案，当前阶段交付计划与评审记录。收到明确实施指令后，才按顺序处理实现草稿。

### 1. 确定工具行为与权限边界

- create_file(path, content) 建议采用严格 UTF-8，逐字节保留传入内容的换行，不自动添加 BOM 或末尾换行；上限 60000 字符，空字符串合法，NUL 和无法编码的文本拒绝。
- 空文件建议沿用 replace_lines(snapshot_id, 1, 1, new_text)。read_file 返回 total_lines=0、empty=true 和虚拟可写范围 1..1；零字节文件及仅有 UTF-8 BOM 的文件均核对原始字节。该参数方案为助手提出，尚未由用户确认。
- 复用任务修改范围、只读任务、单文件目标、固定检查目标及保护路径规则。仅在授权路径下创建缺失的普通父目录；文件排他创建，拒绝已有目标及链接/重解析路径。
- 编辑成功与最终内容一致性分别反馈；创建后核验异常须保留实际副作用信息。写入中断、部分写入和清理失败需要专项评审，失败不能冒充成功，也不能为清理而删除外部后续改动。

### 2. 评审工具与状态链路

按工具协议 → 文件副作用 → TaskRepoTools 策略 → Agent 编辑计数/测试状态 → 事件/结果/Diff → direct 撤回的顺序检查。复用已有撤回机制，按实际缺口决定适配范围。

评审特别核对空的新文件是否具有可导出的创建元数据，以及新建后发生外部修改时的反馈。撤回验收覆盖新增文件删除、已有调用方恢复及冲突整批拒绝。

### 3. 排查现有测试失败，再补足边界检查

已有一次定向离线检查返回 81 passed、1 failed、96 subtests passed。失败位于 tests/test_file_creation.py 的 direct 子场景，撤回后实际为 CRLF，断言预期 LF。该结果来自本聊天工具返回的终端输出，尚无单独保存的验收报告。

推荐排查顺序为记录执行前实际字节 → 比对保存的基线 → 比对修改后字节 → 比对撤回后字节，并核对临时 Git 仓库换行配置。目前不能据此断定是撤回实现错误还是测试夹具假设错误。验收标准为恢复执行前真实字节；若夹具预期写错，应修正其基线依据，不能用忽略换行差异来获取通过。

随后覆盖写入失败/部分写入、同名竞争、已有文件、越界/保护/链接路径、旧快照、外部改动及测试状态失效等场景。每一项记录预期、实际副作用和结果。

### 4. 多文件交付与首批收尾

用脚本模型在 Git worktree、Git direct、普通目录 direct 三种模式完成“新建模块 → 修改调用方 → 运行预先固定检查 → 导出结果”。核对 Diff 包含模块、调用方和空文件，工具事件记录实际路径与应用结果。direct 场景另核对正常撤回和用户后续修改冲突。

首批完成门槛为边界与三种模式全部符合预期、现有相关回归通过、保存检查输出与限制说明。之后再评审第二批定位与上下文反馈的范围。真实模型效果另行授权和记录。

### 本次只读确认的问题

- search_code 默认最多遍历 1500 个候选文件、返回 50 个匹配行。匹配上限触发时返回 truncated=true；文件遍历上限耗尽时仍可能返回 truncated=false，无法据此判断扫描完整。
- 超过 700000 字节的文件和发生 OSError 的文件被跳过，当前没有跳过反馈；单条匹配文本最多显示 240 字符，截短与匹配集合截断也需要区分。
- TaskRepoTools 在 Git direct、普通目录和单文件任务中采用不同的枚举路径。第二批需覆盖这些入口，避免仅修改基础 RepoTools 后仍在子类或过滤之前发生隐藏截断。

### 已实现接口

| 工具 | 参数 | 返回保留项 | 新反馈 |
| --- | --- | --- | --- |
| list_files | 保留 subdir，新增可选 cursor 和 limit；默认页上限沿用 500 | files、returned、limit、scope、supported_extensions | has_more、next_cursor、complete、stop_reason |
| search_code | 保留 query，新增 path，默认为 .，接受单个目录或文件；新增可选 cursor 和 limit，默认匹配页上限沿用 50 | matches、truncated；匹配继续包含 file、line、text | scan_complete、stop_reason、scanned_files、matched_lines_total、skipped_counts、has_more、next_cursor；每条匹配的 text_truncated |

当前沿用大小写不敏感的字面子串搜索。一次选择一个目录或文件范围，Agent 可分次缩小范围。列表 limit 为 1–500，默认 500；搜索 limit 为 1–50，默认 50。搜索每页候选扫描预算为 1500，触发时返回续查信息，列表及匹配文本另受约 25000 字符的输出预算约束。

搜索范围只缩小既有可读范围。allowedPaths 继续表示编辑授权，不能将其直接当作全部可读文件范围。单文件任务、链接、敏感路径、运行材料排除、Git ignore 及文件类型过滤规则须按各入口实际策略核对，并向调用方说明可见范围。

### 完整性与续查语义

1. 文件列表的 complete 表示本次列举已穷尽所声明的可见文本范围。还有后续页时 complete=false，并返回有效 next_cursor。受策略排除的文件不属于该范围，不能把“完整”表述为磁盘上的全部文件。
2. 搜索的 scan_complete 表示整个所选可见范围已经扫描完成，且没有影响结论的读取跳过。matches 为本页结果，matched_lines_total 和 skipped_counts 累计于同一查询的各页；scanned_files 表示本页完成扫描的文件数。只有累计匹配数为零且 scan_complete=true，才能报告该范围内未发现匹配，不能以最后一页为空抹掉前页结果。结论仍限定于工具可见文本。
3. stop_reason 区分 exhausted、match_limit、file_limit、output_limit 等停止原因。大文件和读取错误分别计入 skipped_counts，存在这些覆盖缺口时 scan_complete=false。耗尽候选而仍有跳过时，可以没有续查游标，但必须说明覆盖缺口。
4. has_more 仅表示还有可继续处理的工作，不承诺后续一定存在匹配。达到匹配上限时记录当前文件和续读位置，避免同一文件后半部分丢失；达到扫描预算时能够继续到后续文件。旧 truncated 字段继续提供兼容反馈，具体原因以新增字段为准。
5. 分页在输入未变化时保持确定顺序。游标绑定工具、query 和范围，核对完整候选路径清单及此前已扫描文件的 SHA256，包括同大小且恢复 mtime 的改动。每个 RepoTools 实例保留最近 32 个续查状态；失效、未知或跨范围游标返回错误并提示重新查询。结果为有版本校验的逐次读取，读取后的外部变化仍需后续读取核对。
6. 页大小、扫描预算和输出体积分别约束。恰好达到数量上限时，需核对是否确有剩余工作再决定 has_more。匹配行仅显示前 240 字符时单独标记 text_truncated，完整上下文通过 read_file 获取。
