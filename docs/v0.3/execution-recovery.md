# 步数上限收尾与遗留执行恢复

2026-11-03 增量。验证仅使用临时仓库、独立数据目录与随机端口，不重启用户的工作台，不恢复或重跑真实模型。

## 结束与结果

达到步数上限时保留 stopReason=step_limit、原轨迹、修改、实际检查和未完成事项，进入交付后释放 OS 执行锁。常规状态或结果写入失败时，另存 termination.json 作为终止凭据及部分结果；查询优先读取该凭据，不因 state.json 落盘失败永久卡在 finalizing。部分交付明确标为 delivery.status=partial，不伪造缺失材料或检查通过。若存储整体不可写，不能承诺持久化成功，仍保留服务错误及 unknown，走人工恢复。

## 恢复接口

GET `/api/tasks/{id}/execution/recovery` 返回 `{owner,canRelease,reason,released}`，展示全局遗留 owner；原执行、结果和 diagnostics 仍由既有接口读取。canRelease 只有在取得全局 OS 锁、旧 owner 身份明确、进程检查成功且没有关联活动进程时才为 true。

POST 同一路径，请求 `{"executionId":"待解除的旧执行编号"}`。必须针对 owner 的 taskId 调用；在同一全局锁内重新核对身份与进程，拒绝占用变化、活动执行和核实失败。释放仅保存 recovery.json 凭据，使同一旧 owner 不再阻塞新任务；不删旧 state、轨迹、工作副本，不补造旧结果，不允许同一轮再次启动模型。

进程核对包括锁、当前 worker 线程，以及旧执行目录/副本对应的进程命令和已记录工作台进程的子进程。检查只读，不终止进程。无法枚举进程时拒绝恢复，不仅凭更新时间判断失活。旧记录缺少进程元数据时使用已保存的副本身份和工具日志路径匹配，未知进程信息不作为已确认停止。

网页“异常恢复”展示旧 owner、打开原执行入口和解除按钮。读取与解除是两步，点击解除后仍由后端重新判断；不自动解除、不自动重跑。
