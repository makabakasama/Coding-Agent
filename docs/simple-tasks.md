# 简化任务创建

默认创建页只需要填写本机目标路径与任务描述。目标支持 Git 仓库、仓库子目录、普通目录及代码或文本文件，也可直接选择已登记项目。

任务方式默认“修改代码”，只需分析时选择“只读分析”。版本、修改范围、执行方式、步数及检查权限位于折叠的高级设置。完整契约表单保留在 `#advanced-task`。

## 默认行为

- 默认使用直接模式、50 步，不执行测试。保存后仍需在详情中明确提交执行。
- Git 目标自动识别仓库根目录与 HEAD，子目录和文件自动限定默认修改范围。
- 普通目录使用 `sourceKind=directory`、`baseCommit=null`、`requestedRevision=CURRENT`，工作流不创建 `.git`。
- 单文件任务保存 `targetFile`，读取、搜索与修改都限定在这个文件内。
- 整个项目或目录的修改范围使用 `allowedPaths=["."]`，工具仍排除 Git 元数据、敏感文件、依赖目录及本服务运行材料。
- 本机目标自动登记到项目配置旁的 `local-targets.json`，API 和 Worker 动态读取。同一路径使用稳定项目 ID，便于在项目历史中归档需求与轮次。

浏览器输入的路径属于运行后端的电脑。服务继续只接受本机同源写入请求。目标路径存放在本机配置中，任务公共记录通过项目 ID 关联。

普通目录的读写仍受现有工具支持范围限制，包括代码、HTML/CSS/JavaScript/TypeScript、JSON、Markdown 等文本。单文件选择不支持二进制图片、可执行文件或受保护的配置文件。Git 隔离副本只适用于 Git 目标。

## 提交接口

```json
{
  "targetPath": "E:/Projects/MyApp/app.py",
  "instruction": "修复输入为空时的异常，并说明改动"
}
```

提交至 `POST /api/tasks`。也可用 `projectId` 替代路径。可选字段包括 `kind`、`maxSteps`、`workspaceMode`、`revision`、`expected`、`allowedPaths`、`allowTests` 和 `checkTargets`。默认不运行检查，允许指定检查时需要提供目标，当前检查工具执行 pytest。

后端会将简化请求转换为明确的内部契约，再沿现有数据库保存、队列、Worker 和结果交付流程执行。原始完整契约接口继续可用，历史轮次保持原格式。

直接修改的执行前基线、Diff 与安全撤回同样适用于普通目录和单文件。运行材料与目标目录重叠时，工具会排除材料目录；必要的测试日志放到目标之外，并在本轮材料中保存位置引用。


## 删除与恢复

任务记录页每个轮次提供“删除”按钮，确认后移入回收站。回收站提供恢复和彻底删除入口，最近 50 项按原创建时间展示。项目历史隐藏已删除轮次，全部轮次删除后隐藏对应需求。恢复轮次后重新显示。

删除保留数据库任务、JSON、日志、Diff、撤回材料和工作目录。直接修改过的源码继续保存在项目中，需要恢复源码时使用单独的“撤回本轮修改”。移入回收站阶段保留磁盘材料。

尚未执行的队列任务在删除时退出队列，原调度记录保存在数据库回收站条目中。恢复后须重新明确提交执行。正在准备、执行、整理或状态待核实的任务暂不能删除。数据库事务锁协调删除、入队和 Worker 领取。

接口为 `GET /api/trash`、`GET /api/tasks/{taskId}/lifecycle` 和 `POST /api/tasks/{taskId}/lifecycle`，POST 接收 `{"deleted": true}` 或 `{"deleted": false}`。删除与恢复可重复调用，数据库模式将回收站状态保存在 PostgreSQL，刷新或服务重启后保留。

前端采用乐观更新，确认删除或点击恢复后立即移除当前行，异步提交后端校验。成功时保留本地更新，后端明确拒绝时仅恢复对应行，多个任务独立处理。成功路径无需重新读取完整列表。网络中断或响应无法确认时恢复该行并标为待核实，通过单个任务的 lifecycle GET 查询状态，避免自动重发写入。查询尚未反映操作时继续保留待核实状态，可稍后单独查询。

### 彻底删除

回收站的“彻底删除”需通过独立确认框。后台核对本轮已入回收站、执行已结束、准备及撤回锁可用，再清理数据库轮次与调度记录、该轮历史材料快照、运行目录、日志、Diff、撤回备份及身份已核对的专属 worktree。最后一轮清除后删除对应普通需求记录。其他轮次继续保留，直接模式的原项目源码修改继续保留。

前端确认后立即移除当前行，成功路径使用当前列表状态。失败时恢复该行，响应不确定时通过 `GET /api/tasks/{taskId}/purge` 核实，成功返回 `purged=true`。写入入口为 `POST /api/tasks/{taskId}/purge`，请求体为 `{"confirmTaskId":"完整任务编号"}`。

删除过程在本机任务存储目录的 `purges/` 保存进度。中途中断会在回收站显示“重试清理”，重启后仍可继续，恢复操作在此阶段被禁止。成功凭据只保留任务编号、完成时间及删除状态，用于重复请求核实和阻止旧缓存重新生成材料，运行内容已清除。永久删除会同步使列表及单条任务缓存失效。

## 需求完成状态

结果页分别展示模型停止原因、需求完成状态、实际检查及范围审查。新增结果包含 `completion.status`、`completion.evidence` 和 `completion.modelReported`。旧结果未提供时显示“历史记录未提供”。

修改类任务没有成功编辑却直接声明完成时，Agent 会收到反馈并在原步数预算内继续。现有代码已满足、受阻或未完成时，模型需选择对应 outcome 并提供 evidence。最终没有保留代码修改却报告完成时，结果标为未完成。模型自报完成或现有代码满足仍需审查，独立验收另行记录。
