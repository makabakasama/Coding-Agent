# 通用 Benchmark 执行与逐题准入

每道题独立记录环境、执行和评分三项预检。调度按预注册顺序取可运行的任务，报告继续保留整份清单。开发检查的逐项证据缺失可以降级，官方成绩需要独立的评分证据。

## 职责和输入

| 层 | 输入与职责 | 输出 |
| --- | --- | --- |
| 通用 Harness | 接收已批准的测试入口、工作区和权限，负责工具、模型、预算、超时、状态及原始记录 | Execution Receipt、开发检查回执、运行轨迹、候选补丁 |
| Repository Environment | 优先使用明确的用户配置或固定镜像中的入口与环境，参考固定仓库的公开脚本、CI、依赖锁和初始化说明。将已审核的入口作为 argv 交给执行器。 | 固定源码、可用的执行环境、入口、初始化结果和版本指纹 |
| Test Evidence | 读取与本次运行绑定且格式受支持的机器报告。已有文本解析能识别时可补充诊断，其余情况返回执行回执。 | 用例、套件或仅执行的证据粒度，以及缺失、冲突、截断等原因 |
| Benchmark Evaluator | 独立核验任务、环境和补丁身份，执行官方评分约定，保留原始日志与报告 | `RESOLVED`、`UNRESOLVED` 或 `UNSCORED`、评分器版本和证据引用 |

任务清单固定任务 ID、题面与基准源码版本、运行环境、授权测试目标和官方评分协议。环境差异由配置和镜像承担。公开 CI 中的命令可以作为入口来源，经确认后才执行。需要外部服务或自定义初始化的仓库通过环境清单声明条件。评分日志及隐藏测试放在评估侧，开发请求只含公开任务材料和开发证据。

## 逐题执行和准入

1. **准备工作区。** 核验固定源码与环境指纹，确认依赖、入口和初始化可用。为每个 arm 分配全新工作副本。共享环境故障可以暂停队列，单题环境故障只阻断该题配对。
2. **执行最小探测。** 选择预先声明的无模型执行探测，确认进程能启动，已知退出条件和日志回执能复核。必需开发入口由批次协议预先确定。退出码 0 且回执完整时，缺少可解析报告只降低测试证据粒度。官方基线由各 Benchmark 验证自身预期，例如 SWE-bench 需要能复现目标失败并验证控制测试。基线探测不要求提交修复。
3. **确定评分资格。** 核验固定 evaluator、输入、日志和官方报告。评分能力确认失败或逐项证据矛盾时，登记未评分及原因。已保存的补丁可按预注册的设施重验规则再次评分。
4. **配对并调度。** 每题两组使用相同任务和 G/R、工作区策略、镜像及环境、模型和 Provider 配置、预算、工具权限、官方评分器与评分配置。批次从用户的 `.env` 读取一份模型配置。条件缺失或漂移时暂停该配对并留痕。Harness 提交和模型可见反馈共同标识实验组。

| 状态 | 判定 | 调度 |
| --- | --- | --- |
| `READY` | 环境、必需执行探测、官方评分资格均已核验，且两组条件一致 | 进入有执行授权和资源额度的队列 |
| `BLOCKED_INFRA` | 必需启动、初始化、执行或条件校验存在明确故障 | 保存失败阶段及原因，继续独立任务 |
| `UNSCORED` | 官方评分条件不可用，或评分证据缺失、矛盾 | 保留任务及原报告，跳过正式计分 |
| `PENDING_PREFLIGHT` | 仍缺可复核的预检事实 | 保留待验项，完成后重新判定 |

三项状态和原因分别记录。明确的必需环境或执行错误优先决定主状态，其次是已确认的评分不可用，否则按证据是否齐全判定。用于收集回执的诊断运行单列，成绩仍为空。

已评分成功率为有可信官方结论的解决数除以已有可信官方结论的任务数。报告同时列出预注册总数、已评分数、`UNSCORED` 数和原因、设施阻断数及未运行数。两组胜负只用同条件且两边均有可信官方结论的配对，并列出其占全部计划配对的比例。分母为零时显示“无有效评分”。有评分的真实失败计入分母。重验和原始尝试分别归档。

## 版本边界

| 版本 | Git 提交 |
| --- | --- |
| 历史 P2 | `1c06d2c150ba3df8cd0e496814279377ce50492e` |
| v0.6 RC1 | `2f3b5139c6f39f781df7948121fa6352e63124dd` |
| Execution Receipt v2 | `27dff97293b30b8df5bc5a5225746a8086f64434` |

对三个冻结源码使用同一个小型测试夹具，分别运行共享 Agent 并拦截实际 HTTP 请求构造。三组各拦截两条请求，第二条均带上测试工具反馈。P2 和 RC1 有 `exit_code`，Receipt v2 额外带上 `execution`、`test_evidence`。该差异已在传输前的请求体确认，因此 Receipt v2 必须按独立实验版本记录。后续任何改变工具反馈字段、内容或截断策略的实现也应重新固定实验版本。三份原有提交、工作副本的跟踪内容和 bundle 摘要均已核对。

## 自动化验证

### 新仓库和测试框架

现有 Receipt v2 的 `RepoTools` 从验证清单接收测试 argv，使用本机已安装工具链。只执行公开的指定测试，不安装样例仓库的额外 npm 依赖。

| 公开仓库、固定版本 | 验证结果 |
| --- | --- |
| `google/uuid` · `0f11ee6` · Go 1.20.2 | 公开 `TestUUID` 退出 0，原生 JSON 事件保存在 stdout。现有 Harness 返回仅执行级证据，保留完整日志。使用缺失的可执行文件时，记录 `not_started`、`launch` 和 `INFRA_ERROR`。 [仓库 CI](https://github.com/google/uuid/blob/0f11ee6918f41a04c201eceeadf612a377bc7fbc/.github/workflows/tests.yaml) |
| `HugoDF/node-test-runner-examples` · `7d5c268` · Node 24.19.0 | 公开通过样例分别用原始输出和 JUnit 执行，均退出 0。故意失败样例退出 1。Node JUnit 将 `testcase` 直接放在 `testsuites` 下，当前读取器将其标为 `invalid`，保留 XML，逐项结果为 `UNKNOWN`。生产归因保留进程失败事实，人工可从 XML 中定位断言失败。 [仓库测试入口](https://github.com/HugoDF/node-test-runner-examples/blob/7d5c26892e75091de5b2dd8f297335f069e48ab4/package.json) |

两组成功探测都有完整、哈希一致的 stdout 和 stderr，也都没有为这次接入登记官方 evaluator。执行层可用，Benchmark 状态为 `UNSCORED`。这些探测只覆盖选中的公开目标。

### 既有 10 题和判定逻辑

- 重放官方评分证据得到 9 道基线有效、1 道未评分，官方报告原字节保持一致。
- 按“两个 arm 都具备开发入口回执”的验证假设重放逐题准入，得到 **1 READY、1 BLOCKED_INFRA、1 UNSCORED、7 PENDING_PREFLIGHT**。pytest 的退出码 0 足以证明执行路径，Flask 的启动故障明确阻断，Sphinx 缺官方证据，其余七题缺两组开发入口探测。该结果是设计验证，尚未形成正式批次准入记录。
- 混合队列样例中，两个 READY 任务可以越过未评分和设施阻断的任务。配对分别注入题面、源码、环境、模型、预算、评分器和工具权限漂移，均被判为不可配对。统计样例的五个预注册任务只有两个有效官方结论，成功率分母为 2，另外三项各自留账。

证据和脚本保存在本机 `runs/engineering/benchmark-admission-1443f70b/`。验证共读取 10 道旧题，执行 5 次本机公开入口探测，拦截 6 条本地构造请求。正式 A/B、付费请求和 Docker 容器启动均为 0。

## 未自动覆盖的情况

当前仍需调用方确认公开测试入口和初始化条件，尤其是存在多个入口、依赖外部服务或需要专用镜像的仓库。未知机器报告只支持原样保存。非零退出且缺少可靠用例记录时保留失败阶段或原因待定。未知或矛盾的官方证据保留为未评分。

本轮交付为设计与独立验证。现有 Benchmark 启动器仍使用原整批门禁。接入时应先在 Benchmark 调度层读取逐题清单，再复用现有 Receipt 和官方评分器，并为新的运行组合单独固定版本与实验条件。
