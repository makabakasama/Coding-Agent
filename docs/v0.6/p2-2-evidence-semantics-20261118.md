# P2.2 证据语义与交付状态

## 实现

- 共用的检查回执分别记录执行状态、结果、证据粒度、需求映射和预期来源。`expected` 可写自然语言，`expected_quote` 可单独引用预期。引用无法建立字面对应时保留源码、执行结果及 `NEEDS_REVIEW`。只有具体断言结果能与已核验的预期对应时，才可记为 `VERIFIED` 或 `FAILED`。整个脚本退出码为零只支持检查级结果。
- 批量回执用 `byTarget` 保留各目标的场景结论。临时 unittest 和原生测试保留有记录的独立失败及位置。旧输出和主异常仍可读。对缺失位置、未解析完的用例或截断日志，诊断完整性按可验证材料保守记录。基线混合失败有独立的比较结果。
- `review.gaps` 可登记关键行为和具体的验证目标。反馈突出首个尚未关闭的缺口。缺口在编辑和换测试目标后仍可追踪，只有当前版本已经验证的同一需求及场景才能关闭它。
- Agent、普通任务、Chat 和评测交付分开记录执行结束、模型自报和验收状态。旧收尾门槛继续用于执行层。模型可以结束并自报 `completed`，交付仍显示 `needs_review` 和待验证项。

## 旧轨迹对比

| 证据 | P2 | P2.2 重放 |
| --- | --- | --- |
| Django 候选 | 0 `VERIFIED`，7 `NOT_COVERED` | 7 项 `NEEDS_REVIEW` 保留通过的检查和源码行号。4 项预期仍未核验，3 项缺乏逐用例证据。 |
| Django 关键缺口 | 无单独条目 | 补录独立资源分支的场景。检查每条链内部顺序和虚假冲突告警，比较分组合并及读取中间结果的行为。跨分支固定先后仍无题面依据。 |
| Django 基线 | 只保留第 76 行断言且标为完整 | 分别保留第 67、41、55 行的业务告警和第 76 行断言，保留断言的真实 runner diff。混合失败单列。截断回归按不完整处理。 |
| Django 批量与交付 | 顶层摘要只显示最后一组，自报 `completed` | 批量顶层显示临时脚本 5 项与原生文件 2 项。交付记录 `agent_reported_finished`、`completed`、`needs_review` 和剩余缺口。 |
| SymPy | 3 `VERIFIED`、1 `BLOCKED`、2 `NOT_COVERED` | 三条公开断言维持 `VERIFIED`。临时脚本第 24 行的断言失败保留为实际结果，其预期仍为假设，状态 `BLOCKED`。其他两个场景记录检查级失败与粒度不足，标为 `NEEDS_REVIEW`。旧基线的外层 `SympifyError` 与内层 `SyntaxError` 都保留。 |

Django 重放复用原模型登记的七项映射，独立分支由本轮分析根据公开题面和冻结仓库行为补录。SymPy 沿用 P2 的人工映射。执行结果均来自留存日志。重放未执行官方用例、启动容器或调用付费模型。

## 验证范围与风险

**P2.2 定向离线验收 PASS。** Python 扩展回归 99 项和 11 个子用例通过，覆盖 P0 预算、P1 检查有效性和分类、普通任务交付、容器策略及评分调用边界。两条旧轨迹重放通过。

前端交付状态的两个定向检查通过。完整工作台离线套件 57 项通过、10 项失败。还原本轮唯一的工作台显示改动后，原有的同名 10 项仍失败。Chat 假存储回执通过，专用 PostgreSQL 未配置的集成用例跳过。

模型或审查者仍需登记关键缺口，自动校验无法证明已穷尽题面。聚合脚本通过时只提供检查级证据，复杂或非标准输出可能保留部分诊断。现阶段的收益是保存可审查证据，真实调试行为和官方得分的变化仍缺新运行证据。
