# TEST-01 自测流程优化计划

2026-11-16 已按授权实施，动态验收待进行，见 [实施记录](self-test-quality-implementation-20261116.md)。下文保留经用户确认的计划依据，容器状态隔离实际采用两个串行容器。

## 目标与输入范围

优化 Agent 的测试生成、执行反馈和验证等级，减少错误自测带来的完成误判。模型使用任务原文和固定 G 仓库内可见材料。联网搜索、上游后续提交、解决方案、官方隐藏测试及其断言均排除在修复输入之外。事后失败案例分析留在评测侧。

沿用当前 Agent 循环。需求与测试的轻量核对由当前模型在正常决策中完成，默认不新增模型请求或审查角色。提示与证据字段会增加输入输出 token，前后对照和回归会增加执行时间，具体开销据实记录。

## 当前事实

run_tests 当前只检查应用业务补丁后的代码，完成校验要求当前业务及检查版本有通过记录。本例的实现与断言采用相同错误格式，检查真实通过。

attempt.json 已将 agentStatus 保存为模型自报状态，官方评分另存 Grade。因此本批是在现有结果上补验证证据及汇总等级。模型自报依据和覆盖关系保留其来源，程序不能据此确认断言语义正确。

## 最小实施顺序

### 1. 从任务提取验收条件，核对测试覆盖

让当前 Agent 在编写或修改自测时记录简短验收条件。每条包含任务原文依据、拟验证的触发场景、可观察结果和对应测试位置。原文不足以支持的细节列为假设或待确认项，不能补造精确格式要求。

测试执行前在同一循环核对场景和断言是否对应需求。例如并发需求应具有并发触发，嵌套表达式打印应检查内层格式，字符串转义需检查实际字符。对本例单独区分内部表达式正确与外层格式假设。

程序核对引用和文件版本并保存快照，模型负责说明覆盖理由。字段存在只代表记录齐全。首批优先复用现有计划及观察记录，必要时才增加少量结构化字段，旧 run_tests 调用保持兼容。

### 2. 自动记录修复前后对照

对新增的缺陷回归检查，冻结同一份测试，在固定 G 与当前 G+P 分别执行。记录检查和补丁哈希、实际值与预期值的可用诊断、退出状态、环境异常和日志。

两次执行隔离源码状态、临时文件及 Python 进程，优先在同一个受限容器内组织，总体时间预算覆盖两次执行。缺陷回归应在修复前暴露目标问题、修复后通过；控制测试允许前后均通过。导入、依赖、超时等失败不能计为目标复现。

前后对照仅能说明测试区分了两个版本。本例的错误断言仍可能前失败、后通过，应在验收材料中保留这一反例。

### 3. 运行相关既有回归

按受影响功能选择固定 G 已有的相关测试，保留实际覆盖范围、通过、失败和异常。避免用一份临时脚本替代原有回归。缺少覆盖新需求的既有测试时明确记录覆盖缺口。

业务补丁变化后修复后的检查结果失效，检查内容或验收条件变化后相应覆盖记录失效。沿用当前版本管理逻辑。

### 4. 输出验证等级

保留 agentStatus、开发检查和官方 Grade，增加可解释的验证摘要。

| 状态 | 依据 |
| --- | --- |
| 待复核 | 仅模型自生成测试通过，或验收条件仍有假设、覆盖缺口、缺少所需回归 |
| 开发检查失败 | 当前自测或相关回归实际失败，允许继续修复 |
| 验证未完成 | 超时、依赖或执行环境错误造成证据不足 |
| 独立验收通过或失败 | 对应补丁经既定外部验收产生明确结果；本项目 benchmark 采用官方逐题 Grade |

需求覆盖由模型自报且程序核对引用时，证据类型仍标记为自报覆盖。不能仅凭 acceptance_criteria_verified 之类的布尔值升级到独立验收通过。

### 5. 用 TEST-01 验收流程

评测侧固定旧错误 P 和自测作为案例，验证系统如实记录“自测通过、官方失败”，并保持模型自测通过时的待复核等级。检查当前模型能否指出需求覆盖缺口是后续真实运行观察项，不能提前承诺。

工程验收覆盖前后状态隔离、版本失效、旧调用兼容、失败与环境异常分类、验证等级及串行清理。真实试验使用新轮次和相同允许输入，不把本案例事后官方断言传给模型，最终另行官方评分。

## 实施范围与顺序

先补验收条件与测试对应记录、验证摘要，再接修复前后对照与相关回归，最后按授权验收。主要改动集中在 evaluation/runner.py、development_checks.py、check_runner.py 及必要的进度与工具契约，复用现有代码。

容器始终串行，沿用单容器资源限制、输出归档与结束删除。范围聚焦 Evaluation。工程检查与真实模型试验分别按用户授权执行。

本轮仅修订计划，未修改执行代码、运行测试或调用模型。
