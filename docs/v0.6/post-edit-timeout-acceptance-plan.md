# 编辑后超时与独立恢复评分验收计划

2026-11-20，无付费故障恢复验收通过，见[验收结果](post-edit-timeout-acceptance-20261120.md)。目标是验证编辑和公开检查完成后遇到 Provider 超时，已完成的候选修复仍可从归档独立评分。此项只衡量故障恢复能力。

## 一次无付费验收

1. 使用 Django 12184 已核验的固定提交、镜像和评分配置，新建独立的实验标识、工作副本和空评分目录。保留原 A/B 的首轮结果与 HOLD 状态。登记本次求解代码指纹、模拟 Provider、检查配置和评分运行时。模拟请求和用量只记入验收账本。
2. 在正常 Agent 工具入口按脚本完成一次非空业务编辑和一次已有公开测试。可以重放 A 组公开编辑和检查动作；不读取官方隐藏测试来决定如何编辑。保留编辑 diff、公开测试回执、原始输出、对应候选哈希。测试回执必须已落盘。
3. 在下一次模型传输请求注入超时，禁用真实 Provider 网络访问。让通常的错误处理、补丁导出和账本结算自然结束。记录事件顺序、终止原因和实际请求次数。校验已知用量、未知尝试、保守计账、最终在途预留为零；模拟值与 Provider 实报分列。
4. 在候选补丁与 attempt.json 已落盘、批次 slot 的 result.json 尚未发布处设置中断边界。保留匹配登记的 intent.json、worker.json 及运行产物。使用独立目录并记录初始状态，确认没有旧评分指针。新进程用 start_limit=0 调用 run_queue()，记录确实进入 recover()、取得新评分报告，恢复期间没有模型请求。若队列因已有 result.json 跳过，应记为未覆盖该路径。核对实际评分的冻结基线、独立副本和运行时。
5. 分别记录公开测试用补丁、归档补丁、预测记录中解码后的补丁、评分器实际应用补丁的字节数、SHA256 和产物引用。若开发检查与最终导出使用不同 diff 格式，先记录两种原始哈希，再分别将补丁应用到相同基线并核对所得 Git tree。归档、预测与评分器输入之间要求实际补丁字节一致。

执行超时与补丁官方 PASS/FAIL 分列。可信的官方 FAIL 也能完成恢复验收。缺少非空补丁、检查回执、可闭合账本、独立评分或补丁身份核验，均须记录具体缺口并保留本次结果。

## 真实模型实验申请草案

建议候选题为旧登记中尚未正式启动的 pytest 9359，顺序 B → A。若评估测试目标准入改动，另建单变量注册，两组从同一求解源码起点冻结，唯一差异为准入修复，固定相同的虚假 PASS 处理、收尾和预算。沿用公开题面，不预设该题一定会触发差异。旧虚假 PASS 实验继续 HOLD。

申请限一题两次，各一次首次运行。拟使用 gpt-6-luna、温度 0、500K 本地计账上限、50 次决策、1,800 秒软超时、传输重试 0；总名义准入额度 1,000,000 Tokens。执行前重新核对两组版本、模型可用性、镜像及评分条件。超时、评分设施异常或账本无法闭合先停队列，保留原结果。零补丁单列未评分。共享评分故障优先恢复同一份补丁。无自动重跑或扩题。

无付费验收通过后再申请真实运行。报告官方通过数 / 已启动任务数、各组 PASS/FAIL/未评分、公开测试准入是否实际改变工具行为、已知与未知用量。一对实验用于确认机制及交付链路，无法估计总体通过率提升。

### 交叉核对后确定的执行边界

旧预检中 pytest 9359 的指定公开检查在两组均可运行，真实模型是否选择其他目标未知。两组须共享写保护、导出检查和评分规则。实验变量仅限测试目标准入。

上文的停止条件是申请约束。目前调度器能因评分故障暂停，无法保证遇到模型超时后停在半对。不能把初始 max-starts=1 当成逐组执行。若申请时沿用现有调度器，应明确按一整对授权，Provider 超时按实际结果留档，完成这一对即停止，不再追加；若要求首组模型超时即停，则须先以无付费方式证明调度能执行这个条件。
