## 配对执行

1. A 为 v0.6 RC1，B 为历史 P2，使用审核报告中的两个 Git bundle 与提交。每道题每组从固定 G 重新建工作副本，锁定同一题面、同一模型与 Provider 配置、标准权限提示、预算、开发镜像摘要、资源限制和官方评分器。按样本清单顺序交替 A→B、B→A，登记实际顺序及网关标识。没有同一 Checkpoint 时，比较完整 Harness 的端到端行为。 [RC 审核报告](release-candidate-20261119.md)
2. 付费前以 Django 15400、Sphinx 8627、Matplotlib 26011 做轻、中、重三题的无模型资源预检，按结果扩展到其余样本。每题核对固定 G、镜像源码和基线。基线必须能复现目标失败且控制测试通过。基线基础设施失败保留为未判定，在同一固定输入上可做一次设施级重验。样本表与预检结果一起冻结。计划 10 题全部保留在报告分母，若可评题少于 8 道，先处理实验设施。
3. 容器保持串行、1 GiB。两组使用相同的网络与可见材料约束，模型只接触公开题面、固定仓库和开发检查。官方隐藏测试、标准补丁及判分细节由评分侧隔离。按候选补丁 SHA-256 在固定镜像中独立评分，保存应用状态、`resolved`、目标与控制计数。空补丁、模型或工具失败、预算停止、设施异常和未运行分别记账。
4. 逐 HTTP 尝试保存输入、输出、缓存、推理明细、未知用量和账本结算，关联每次工具反馈、测试分类、编辑与补丁哈希。保存模型自报、执行状态、Harness 验收与官方成绩四个字段。主指标为**全部计划任务上的首次 `resolved`**，另列可评分分母和配对胜负。用量、有效调试闭环、首个有效开发检查、资源峰值与耗时为辅指标。费用按账单拆分，失败尝试继续纳入。候选补丁评分失败先判断设施原因，同一补丁允许追加一次评分，避免重复调用模型。
5. 每批启动时从项目根目录的 `.env` 读取一份模型和 Provider 配置，整批 A/B 共用。历史模型只用于解释已有记录和成本估算。归档仅记录实际模型、配置档和非敏感运行信息。

## 重复策略

首轮 **10 题 × 2 组 × 1 次**。完成后最多选 3 题做第二次完整配对，两组各开一份新副本。排序先取首次官方结论不同的配对，其次取一组因预算收尾或两组实报相差至少 100,000 token 且比值至少 1.5 的配对，再按题号确定并列顺序。首次差异仅作为复核线索。若未出现触发条件，可预先用一轻一重作为稳定性抽样，分别为 Flask 4045 和 SymPy 17630。重复批独立授权和报告，保留首轮结果，同时列出重复子集两次均过、至少一次通过和用量范围。定向复核子集的结果保持该子集口径。
