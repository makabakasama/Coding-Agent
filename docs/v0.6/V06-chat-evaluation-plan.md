## 目标与本轮依据

首个交付场景为用户在同一会话中讨论问题、读取项目、明确需求、发起授权执行、查看工具与补丁，再继续追问。同期建立能评价这条路径的任务集、记录和独立评分入口。

项目总入口为 [推进计划](../plan.md) 与 [项目状态](../status.md)。本草案制定时已读取求职目录的 PLAN.md、STATUS.md、项目 AGENTS.md、V0.4/V0.5 状态及关键实现，相关项目计划和状态现已归入 docs。当前已有 PostgreSQL 调度、独立 Worker 池、代码定位与编辑工具、进度/预算、事件/结果、Diff 和历史入口，继续复用。

关键实现依据如下。

- `core/agent.py` 的 `Agent.run(task)` 每轮新建 `RunContext`，当前运行内历史无法直接提供跨用户轮次的会话状态。
- `core/provider.py` 的 `decide(messages)` 返回工具决策，响应交给 `parse_tool_decision`。普通自然语言回复需要显式协议支持。
- `core/context.py` 已记录输入指纹，Provider 已采集可用 token 字段，可作为新记录契约的基础。
- `backend/repositories/task_queue.py` 的调度行关联既有 task_runs，`queued_execution.py` 入队依赖项目与工作副本。无项目的普通聊天需要自己的持久调度关联。
- 当前前端为原生 JavaScript，后端为标准库 HTTP。首阶段沿用现有技术栈，新增职责按当前分层组织。

当前工作区有既有未提交改动。将来记录 Agent 版本时，同时记录 HEAD 与相关未提交源码指纹/快照，单独一个 commit 不能代表本地执行版本。本轮没有验证历史测试结果在当前源码上仍成立。

## 首版范围与核心流程

### 普通聊天

用户新建会话，可不绑定项目。支持普通问答、需求讨论和连续追问，历史持久保存。首版按完整响应展示，轮询状态与事件，流式文字作为后续体验增强。

### 项目讨论

用户关联一个本机项目/目录后，讨论轮可使用列表、搜索、读取工具。服务端限制工具权限，读取结果记录文件版本与引用位置。绑定路径不会自动把整个项目加入模型输入。

首版一个会话关联零个或一个工作区。已有对话改绑项目时，新建会话并可携带经用户选择的摘要，避免旧项目证据混入新项目。不同会话可关联不同项目。

### 从讨论进入执行

讨论结果形成可执行目标。用户可通过明确的执行操作提交目标、路径范围、direct/worktree、预算和测试权限。入口在对话内展示这些设置，允许编辑；已有明确授权和完整设置时直接提交，无需再次讨论同一授权。

模型提出的执行建议只生成待执行草案。后端依据本轮显式提交的权限决定可用工具。普通发送消息默认保持讨论权限，避免将模糊的“继续”解释为写入授权。

每次执行保存当时的需求、上下文截止点和权限快照，再创建一个新的普通任务轮次，复用准备、队列、Worker 和 Agent。现有 task_dispatch 每个 task_id 对应一轮执行，后续修改使用新的 task_id，并通过会话关联。

执行结束后，对话展示摘要、实际状态、修改/检查入口及未验证项。用户可以继续询问原因或提出下一轮修改。新轮重新读取需要引用的文件，旧工具快照只作为历史证据。

### 首版运行中交互

同一会话一次推进一轮，运行期间保留输入草稿并明确提示等待当前轮结束，发送入口暂不可提交新轮。首版不承诺在途指令注入、任意中断续跑或分支编辑历史。多个会话的运行仍遵循既有 Worker 容量与工作区冲突约束。

若后续增加停止能力，再单独设计排队取消、模型请求边界、部分修改和证据保留。主动取消保留为配套候选项。

## 会话与运行数据契约

以下为建议的逻辑对象，详细设计时再映射数据库表和接口。

| 对象 | 必备信息 | 约束 |
| --- | --- | --- |
| Conversation | id、标题、可选 workspace、创建/更新时间、revision | 不同会话上下文隔离 |
| Message | id、conversation_id、顺序、role、content、turn_id、时间 | 消息顺序稳定，首版追加保存 |
| Turn | id、client_request_id、输入 message_id、历史截止点、模式、权限快照、状态、响应引用 | 客户端重发同一请求返回同一轮 |
| ExecutionLink | turn_id、task_id、execution_id、材料引用 | 一次执行轮关联一个普通任务，后续轮另建任务 |
| ContextManifest | 消息范围、选中文件及版本、运行摘要引用、组装版本、输入指纹 | 能追溯模型实际看见的输入 |
| UsageRecord | 调用/尝试标识、模型与配置指纹、时间、用量可用性、token 字段 | 未提供的用量保留 unknown |

讨论轮包括普通文字生成和可选只读工具循环。执行轮由既有任务状态驱动，Turn 保存关联与会话层状态，避免独立复制一套执行事实。

建议 Turn 状态为 queued、running、completed、failed、unknown。completed 只表示本轮响应或执行材料已形成，任务是否成功另存评价。Worker 丢失心跳或响应落库结果不明时进入 unknown，保留人工核对入口，避免自动重复有副作用的执行。

普通聊天也需要持久轮次队列，建议增加会话轮次调度记录，由现有独立 Worker 池分派讨论处理器；执行仍进入既有任务队列。复用领取、心跳和容量约束所需的小范围代码，先完成垂直接入。设计阶段核对双类作业公平性，以及等待执行任务的会话轮不得占用线程等待子任务，避免所有槽位被等待者占满。

提交轮次时，在事务内保存用户消息、Turn 和讨论入队信息；执行草案确认后的任务创建、关联、入队需要可重入步骤及恢复标记。唯一请求键、会话 revision 与活跃轮约束共同处理双击、多个标签页和超时重发。模型返回后，响应落库与轮次结束保持事务一致，事件带递增序号供刷新后去重恢复。

上下文建议由固定系统约束、选定会话消息、必要的运行摘要/只读证据和最新状态组成。工具调用与结果成对纳入。保存可脱敏的输入材料及指纹，只有哈希无法重建实际输入。首版设置明确的上下文上限，超限提示用户缩小范围或另开会话，后续再设计有可见记录的摘要压缩。

建议接口覆盖会话创建/列表/读取、消息分页、轮次提交/状态/事件，以及执行草案确认。HTTP POST 返回持久轮次 ID，模型请求交给 Worker。普通聊天无仓库依赖，禁止通过虚构仓库绕过当前队列契约。

Provider 增加明确的文本回复/工具调用结果表示，共享配置、HTTP、重试、脱敏与用量采集。既有编码 `decide()` 调用者继续接收原决策类型；工具能力由程序按模式提供并在执行时复核，UI 标签和提示词共同服务于后端权限。

## Evaluation 最小闭环

### 数据契约

| 对象 | 最小内容 |
| --- | --- |
| TaskSpec | schema_version、task_id/version、类型、开发/保留划分、输入/多轮脚本、环境/基线与哈希、允许操作、预算、冻结验收规则及检查器版本 |
| EvalRun | run_id、任务版本、重复轮次、Agent HEAD 与本地改动指纹、模型/非敏感配置、Turn/Task/Execution 关联、起止时间、终止原因、材料清单及哈希 |
| Grade | run_id、grader/version、各项 pass/fail/unknown/skipped、证据引用、评审来源、失败分类、人工评语 |
| Report | 数据集/配置版本、计划/实际样本数、各结果及分母、重复轮次、用量完整性、耗时/步数/成本分布 |

聊天和代码任务共享运行索引，各自保留适用材料。聊天任务保存多轮输入、回复和工具证据，编码任务继续保存基线、补丁、检查及独立验收。数据集与检查器进入源码版本管理，完整运行材料按现有 runs/ 约定留存。

执行记录、模型 completion、工程检查、任务评分和独立验收分别记录。评分器读取冻结规则与原始产物，重评分生成新 Grade，保留原评分。真实仓库修复实验继续遵循 AGENTS.md 的 G/R/P 与独立副本流程。

### 首批样本建议

先准备 12 个小型场景，建议 8 个开发样本、4 个保留样本，在运行前冻结划分。覆盖以下六类，每类两个不同输入或项目变体，保留集覆盖其中四类。

1. 无项目问答与多轮约束延续。
2. 项目读取、定位和基于文件的解释。
3. 需求讨论与权限边界，包括只讨论修改方案的请求。
4. 明确授权后的单文件及跨文件修改。
5. 执行结果追问、后续修改和文件已被外部改变的情况。
6. 工具/Provider 失败、预算耗尽及未运行检查的如实交付。

在此之外，把重复提交、会话隔离、刷新恢复、断线、Worker 故障等确定性问题列为工程验收矩阵。脚本模型用于验证程序行为，真实模型结果单独记录。保留样本一旦用于调参，就需要另补新保留样本。

首批编码样本使用可重建的小仓库和固定检查，聊天场景优先检查关键约束、引用和禁止行为。开放回答使用固定人工 rubric，逐项判断事实依据、需求覆盖与交付诚实性，保留评审者身份和判断。首版先形成逐项结果，待维度含义稳定后再确定综合分权重。

### 判定与比较

- 记录运行终止情况、目标满足情况、约束遵守情况、检查证据及独立验收状态。权限违规作为必须单列的失败。
- 失败分类允许主因加次因，例如需求理解、定位、修改、工具/协议、环境/依赖、Provider、预算、权限、验收设施和证据缺失。
- 首报同时给出通过数/计划总数、通过数/可判定数，列出失败、unknown、skipped 和未运行数量。环境阻塞归类后仍保留在总体结果中。
- token 缺失保留 unknown；失败尝试可能已产生费用，用量覆盖不足时成本标记不完整。价格表需记录来源、日期和币种，无法取得可靠价格时只报告原始用量。
- 首轮建议一个现有模型配置、每个样本一次，用于建立故障清单。真实调用前再明确配置、调用预算、单次/整体上限和停止条件。每轮运行到上限均留档。
- 版本或模型比较作为下一批工作，固定任务版本、环境、预算和评价器，并保留重复轮次。小样本报告描述观察结果，求职材料展示具体样本、分母及证据。
